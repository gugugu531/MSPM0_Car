# 静止稳球 0 cm：上板与机械标定

当前 `H3 Ball Static` 完成的是第一阶段：小车静止时，利用树莓派返回的球位置/速度把球
守在 0 cm。完整的 `O → +5 cm → -5 cm` 时序尚未接入。

## 1. 已确认的坐标方向

机械方向已经确认：

```text
cnt 增大 → 水管正倾 → 球向视觉正方向加速
```

因此树莓派必须使用同一个定义：球向上述方向运动时 `X` 和 `V` 均增加。可先手推球验证
`Device Check -> Rpi UART` 页面；方向相反时优先改树莓派坐标映射，不要在多处各翻一次符号。

## 2. 非线性连杆映射

固件不再使用常数 `deg/count` 的线性近似。当前映射直接来自根目录自包含的
`pygame_linkage_visualizer.py` 精确槽约束模型，其最新物理参数为：水管长 `24.707 cm`、
合页轴 `(19.0, 8.3) cm`、电机轴 `(0, 3.2) cm`、曲柄半径 `5.0 cm`、水管轴线到槽中心
`1.894 cm`、槽中心到打印件底面 `0.7 cm`，编码器 `2000 cnt/rev`（`0.18°/cnt`）。

- 当前按用户指定值将水平位置标定为 `180 count`；
- 机械全行程 `0~450 count`，现有安全软限位仍为 `20~430 count`；
- 软限位对应的模型倾角约为 `-5.345°~+5.236°`；
- `160/180/200 count` 分别约为 `-0.615°/0°/+0.594°`；
- 水平附近局部增益约 `0.03024°/count`，并随 count 增大逐渐下降。

为避免 Cortex-M0+ 每拍反复计算 `asin/atan2`，固件使用每 20 count 一个点的单调查表并做
双向线性插值：编码器计数用于计算实际水管角，目标水管角反查目标计数。对新几何模型在
`20~430 count` 全区间逐 count 扫描，最大插值误差约 `0.006127°`（出现在约 410 count）。

本次将此前的 220 count 水平先验整体移到 180 count，并同步重生成整条查表，而不是只改
显示标签。首次上板仍建议在 `20/160/180/200/430 count` 等点用角度仪抽查；若整条曲线
表现为统一平移，应继续修正模型的 count 相位，而不是重新退回单一斜率。

### 2.1 任务范围内的近似关系

H3 基础控制限角约为水管 `±4°`，在当前名义几何下对应 `59~339 cnt`。令电机轴相对
180 cnt 的转角为 `phi_m=(cnt-180)×0.18°`，这一范围是 `-21.78°~+28.62°`。
对根目录 `pygame_linkage_visualizer.py` 的逐 count 真值拟合得到：

```text
仅线性：theta = 0.1570566 phi_m
  RMS 0.234°，最大误差 0.548°                -> 不可直接用于控制

三次名义近似：
theta = 0.1681067 phi_m - 8.0079e-4 phi_m² - 7.2377e-6 phi_m³
  RMS 0.000762°，最大误差 0.00237°           -> 可用于量级分析
```

水平点局部传动增益约 `dtheta/dphi_m=0.1680`。滚球名义动力学为：

```text
a_ball = K_G sin(theta - theta0)
K_G = (5/7)g = 7004.75 mm/s²/rad（名义值）
```

在 `|theta|<=4°` 内，小角度斜率约 `122.256 mm/s²/deg`，完整正弦与线性式最大只差
`0.40 mm/s²`。但若跳过连杆模型，直接对电机角使用单一线性加速度系数，最大误差达到
`66.8 mm/s²`；三次名义关系的最大误差约 `0.242 mm/s²`。

因此固件仍采用“编码器 count -> 名义连杆查表 -> 校正水管角 -> sin 动力学”，三次式只用于
解释和离线核对，不形成第二条控制分支。考虑尺寸和角度测量误差，所有需实机辨识的值集中在
`app/app_ball_config.h`：`APP_BALL_LINKAGE_ANGLE_SCALE`、
`APP_BALL_LINKAGE_ANGLE_OFFSET_DEG`、`APP_BALL_ROLLING_GAIN_MM_S2_PER_RAD` 和
`APP_BALL_INITIAL_ZERO_TRIM_DEG`。修改比例/零点后，正向查角和反向下发 count 会同步生效。

### 2.2 动力学零位

不要用“球静止不动”直接找零：PPR 接触蠕变和滚动阻力会给出一段假零区。应让球保持缓慢
滚动，在零位两侧给数个小计数偏置，由树莓派速度变化估计加速度，分别拟合正向和反向：

```text
a_ball = A × cnt + B
cnt_zero = -B / A
```

取两个方向所得零点的中值用于检查几何模型基准。由于当前水平相位仍有约 `±0.6°` 的
不确定性，控制器启用受监督的小范围零偏学习：只在中心低速、链路健康且没有制动/卡滞
迹象时积分，失去许可后缓慢泄漏，避免人工拨动或工具截停永久污染偏置。

### 2.3 精简后的在线终端约束控制

旧版“三段停止距离 + tanh 速度候选 + 反解制动速度”的两套包络已经删除。当前每个 20 ms
控制拍只完成一次统一规划：从最新实测 `(x0,v0)` 和由实际水管角得到的 `a0` 出发，规划到
`(target,0,0)` 的五次轨迹：

```text
x(t) = x0 + v0*t + a0*t²/2 + c3*s³ + c4*s⁴ + c5*s⁵,  s=t/T
x(T)=target, v(T)=0, a(T)=0
```

三个终端条件唯一确定 `c3/c4/c5`，因此完整规划严格满足：

```text
integral(a dt) = v(T)-v0 = -v0
integral(v dt) = x(T)-x0 = target-x0
```

需要特别区分：只有规划起点也静止时，加速度积分才是 0；外界拨动后 `v0!=0`，正确约束应是
`integral(a dt)=-v0`，否则终点速度不可能归零。规划时长先由名义最大速度、最大加速度和
最短时长估计，再对真实五次曲线采样并迭代拉长；初始状态已经越限时仍保证终端约束，同时
通过 `lim=1` 明确报告运动上限被继承状态放宽。

控制器不是一次性跑完整条轨迹。每拍都按最新 `(x,v,theta_actual)` 重新规划，只取前方
`lookahead=120 ms` 的参考点后再次规划，因而工具释放、外界拨动和模型误差会在下一拍进入
新边界条件。输出为：

```text
a0        = K_G sin(theta_actual-zero_trim)
theta_ff  = asin(a_ref/K_G)
theta_fb  = Kx*(x_ref-x) + Kv*(v_ref-v), clipped to +/-1.5°
theta_cmd = zero_trim + theta_ff + theta_fb
```

名义参数为 `vmax=90 mm/s`、`amax=280 mm/s²`、`T=0.35~3.0 s`、
`Kx=0.025 °/mm`、`Kv=0.018 °/(mm/s)`。这些全部是 `app_ball_config.h` 或 H3 配置中的集中
可调项，不是不可修改的测量真值。基础控制角限制为相对动力学零位 `zero_trim±4.0°`；最终
仍受修正后的连杆角范围和编码器软限位保护。

角度变化率按位置误差调度：

```text
rate_normal = 40 + (70 - 40) / (1 + (|error| / 30 mm)^2)  [deg/s]
rate_brake = 100 deg/s, when velocity × a_ref < 0 and |velocity| > 5 mm/s
```

普通纠偏中心附近约 `70°/s`、远端渐近 `40°/s`，仍维持近端比远端快；规划加速度正在
消除现有速度时临时提高到 `100°/s`，优先卸掉动能。

当 `|error|>=20 mm`、树莓派报告 `MOVING=0`、连续位置变化不超过 `0.5 mm`，同时控制器仍
请求至少 `1.2°`，持续 `0.8 s` 后才标记工具截停或卡滞。该标志只用于 OLED/Debug_Ex
诊断和冻结慢积分，不再把倾角压向名义 `±0.7°`；仅凭位置无法可靠区分工具截停与静摩擦，
自动回名义小角仍可能形成隐蔽的 safe return。

零偏在 `2<=|error|<=20 mm`、`|v|<=8 mm/s` 且链路健康、无边缘、无制动/卡滞且规划
没有继承超限状态时，以 `Ki=0.004 °/(mm·s)` 学习，限制为 `±0.6°`。依据实测
`a≈129×beam+50`，H3 以 `-0.40°` 作为动力学零位初值；它不触发进入时的角度回归，
只用于控制模型和反馈基准。不满足学习条件时按 `180 s` 时间常数缓慢泄漏。

## 3. 启动条件

H3 按“树莓派回传足够可靠”的策略接管：

- 球在中心 ±120 mm 内，覆盖水管主要有效区域；
- 收到过一帧 CRC 与协议版本正确的 `VALID=1` 数据；
- 总测量龄不超过 200 ms；只需一拍即可接管。

`QUALITY`、`V_VALID`、60 ms 降级标志和之后偶发的单帧 `INVALID` 仍会显示和统计，
但不再让 H3 退出闭环。单帧无效时继续使用最近一次有效位置，直到 200 ms 总超时。

控制器内部稳定判据为 `|x|<=2 mm`、`|v|<=5 mm/s` 连续 1 s。基础控制命令为 `±4°`，
动态角速度为普通 `40~70°/s`、制动 `100°/s`；零偏只在监督窗口内学习。最终目标仍会被
`-5.2°~+5.1°` 的保守连杆物理边界和步进电机编码器软限位夹住。

## 4. 失效行为

- 单个 `VALID=0`、速度标志或质量不足：继续使用最近一次有效位置闭环；
- 进入 H3 时保持当前水管角等待首帧视觉，不先去机械水平标定位置；
- 总测量龄超过 200 ms：立即停止脉冲并保持失链瞬间的水管角，等待视觉恢复；
- 退出 H3 时同样就地保持，不自动回水平位；
- 步进限位守护进入 `FAULT`：任务进入系统故障页，驱动层已经停机失能。

这里刻意不使用几何模型的水平 count 做 safe return：水平标定存在偏差时，盲目
回零可能形成持续斜坡并把钢珠送到水管一端。通信恢复后，控制器从实际保持角重新初始化，
再由树莓派位置反馈接管。编码器机械软限位仍然全程有效。

## 5. 首次上板顺序

1. 抬起/取下球，验证进入 H3 后水管就地保持，不能先自动回某个水平 count。
2. 用 UART 测试发送器分别发送 `x=+10 mm` 和 `x=-10 mm`：前者必须令目标 cnt 下降，后者上升。
3. 接真实视觉，手推球确认 `X/V` 符号、帧率、测量龄和 `QUALITY`。
4. 将球放在中心附近，扶住两端挡片后短时闭环；先核对方向，再逐步放手。
5. 用 `Debug_Ex/UART1`（115200 8N1）记录 `[BALL]` 遥测，再调整机械标定值和控制增益：

   ```powershell
   python tools/visualizers/ball_balance_viz.py --port COM7 --csv ball.csv --log ball_raw.txt
   ```

   H3 输出树莓派原始/控制位置 `xr/x`、原始速度 `v`、目标误差 `et`、预瞄参考
   `xref/vref/aref`、规划时长/预瞄 `T/look`、规划峰值 `pv/pa` 和由实际水管角得到的初始
   加速度 `a0`。`ia/iv` 是完整规划的加速度/速度积分，应分别等于 `-v` 和 `et`；
   `rx/rv/ra` 是终端位置、速度、加速度残差，正常只剩浮点舍入误差。
   `aff/fbp/fbv` 分别是模型前馈、位置反馈和速度反馈，`motor/beam` 同时给出电机相对水平轴角
   与查表水管角，便于继续辨识传动关系。`lim=1` 表示初始状态已经超过名义运动上限，规划为
   保持终端可达而继承了该超限状态；`mspd/mkp/sf` 是步进位置伺服轴速、增益和 STEP 频率，
   `arr/cc/ctr` 是 TIMG6 实际寄存器，`sdt/smax` 是步进 10 ms 调度最近/最大间隔；并用
   `rl/brk/stuck/px` 标识斜率限制、制动、截停和匀速位置补偿。它也回传零偏、限幅状态和
   树莓派链路统计；进入任务时的 `[BALLCFG]` 行给出本次固件实际使用的全部关键参数。若 `drop` 持续
   增长，说明 Debug_Ex 输出缓冲来不及发送，此时采样不完整，应先排查串口连接或降低输出频率。

## 6. OLED 实时页面

H3 页面以约 `10 Hz` 更新 `x/v`、编码器当前/目标计数、命令角/零偏和测量龄/质量。
此前页面在 `ACTIVE` 状态只在状态或 `settled` 翻转时渲染，导致闭环数据实际持续变化，
OLED 却长时间停在接管瞬间的旧值。这是应用层刷新门控造成的确定性冻结，并非树莓派停止
回传或 OLED DMA 失效。

旧门控建立在“整帧 OLED 刷新会阻塞约 26 ms”的历史假设上；当前驱动已经采用双缓冲 DMA，
约 23 ms 的 I2C1 整帧传输在后台完成。H3 现在对所有状态按 100 ms 周期请求刷新，并在
`Ui_IsFlushBusy()` 为 true 时直接跳过该控制拍，不调用会等待上一帧完成的 `OLED_Flush()`。
状态变化若恰逢 DMA 忙，不会丢失：渲染快照仍保持旧值，后续 20 ms 控制拍会继续重试。

当前仍有一项架构债务：RUN 模式下 `App_UiTick()` 不渲染，任务只能在自己的 20 ms 控制
回调中调用 UI。忙时跳过已避免已知长等待，但长期更合理的做法是给任务增加独立
`on_ui_tick`/状态快照，让控制计算与 OLED 文本格式化彻底分离。完整高速诊断仍以 20 Hz
Debug_Ex `[BALL]` 为准，OLED 只承担现场概览。

## 7. 2026-07-31 串口实测发现

此前记录中，球位置长时间稳定在约 `7.7~8 mm`、树莓派 `MOVING=0`，但旧 H3 遥测速度仍约
`-6.8 mm/s`。串口帧率、CRC、丢帧和 Debug_Ex 丢字节均正常，因此问题不在树莓派数据质量，
而在 MCU 的 `RpiUart_Predict()`：它无条件叠加
`a=(5/7)g sin(theta)`，忽略静摩擦，在约 `-1.3°` 水管角和约 `43 ms` 测量龄下凭空生成了
速度。正式扰动日志还显示旧 `zero_trim` 会在人工拨动期间被改写，并在截停后保留约
`-1°` 偏置。

H3 现改用 `RpiUart_Observe()`：静止时原样使用树莓派 x/v；仅在 `MOVING=1` 时用原始速度
对位置做匀速时延补偿，绝不按水管角生成加速度或速度。旧 `RpiUart_Predict()` 暂时保留给
其他诊断页面，避免扩大本次修改范围。实测原始记录和分析报告位于工作区
`captures/h3/h3_20260731_010540_*`；事件键存在最多约 30 s 的人工标记滞后，判断扰动/截停
时刻应以位置、MOVING 和 INVALID 变化为主，不把事件键时间当作精确真值。

以下结论针对已删除的旧“双速度包络”，保留作为本次精简的历史依据。2026-07-31 采用
180 cnt 水平相位的 20.16 s 记录共 337 帧。离线重算显示全部 337 帧均为
`vc<vb`，制动候选一次也没有成为最终包络；同时大误差区的 `vc` 长期接近 `65 mm/s` 饱和。
因此当时曲线上看不到预期的“制动支路压低目标速度”并非绘图遗漏，而是当前参数组合确实
让 `min(vc,vb)` 退化为 `vc`。后续 450 帧记录进一步确认 `esrc=1` 为 0，并发现电机轴
`60°/s` 被误当成水管角速度；完整量化和整改见
[`h3-control-data-analysis-20260731.md`](h3-control-data-analysis-20260731.md)。
