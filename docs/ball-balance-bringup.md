# 静止稳球 0 cm：上板与机械标定

当前 `H3 Ball Static` 完成的是第一阶段：小车静止时，利用树莓派返回的球位置/速度把球
守在 0 cm。完整的 `O → +5 cm → -5 cm` 时序尚未接入。

## 1. 已确认的坐标方向

机械方向已经确认：

```text
cnt 增大 → 水管正倾 → 球向视觉正方向加速
```

因此树莓派必须使用同一个定义：球向上述方向运动时 `X` 和 `V` 均增加。可先手推球验证
`Device Check -> Rpi UART` 页面；方向相反时优先改树莓派坐标映射，不要在多处各翻一次符号。

## 2. 非线性连杆映射

固件不再使用常数 `deg/count` 的线性近似。当前映射直接来自根目录自包含的
`pygame_linkage_visualizer.py` 精确槽约束模型，其最新物理参数为：水管长 `24.707 cm`、
合页轴 `(19.0, 8.3) cm`、电机轴 `(0, 3.2) cm`、曲柄半径 `5.0 cm`、水管轴线到槽中心
`1.894 cm`、槽中心到打印件底面 `0.7 cm`，编码器 `2000 cnt/rev`（`0.18°/cnt`）。

- 水平位置实测只确定在 `200~240 count`，模型名义相位取 `220 count`；
- 机械全行程 `0~450 count`，现有安全软限位仍为 `20~430 count`；
- 软限位对应的名义倾角约为 `-6.785°~+4.801°`；
- `200/220/240 count` 分别约为 `-0.615°/0°/+0.594°`；
- 水平附近局部增益约 `0.03024°/count`，并随 count 增大逐渐下降。

为避免 Cortex-M0+ 每拍反复计算 `asin/atan2`，固件使用每 20 count 一个点的单调查表并做
双向线性插值：编码器计数用于计算实际水管角，目标水管角反查目标计数。对新几何模型在
`20~430 count` 全区间逐 count 扫描，最大插值误差约 `0.005388°`（出现在约 410 count）。

几何公式精确不等于水平相位准确。真实水平若分别位于 200 或 240 count，则名义 220 count
处约有 `+0.594°` 或 `-0.615°` 的倾角偏差。首次上板应在 `20/200/220/240/430 count`
等点用角度仪抽查；若整条曲线表现为统一平移，应修正模型的 count 相位，而不是重新退回
单一斜率。该不确定性也已作为 `level_count_min/level_count/level_count_max` 写入 Python 模型。

### 2.1 动力学零位

不要用“球静止不动”直接找零：PPR 接触蠕变和滚动阻力会给出一段假零区。应让球保持缓慢
滚动，在零位两侧给数个小计数偏置，由树莓派速度变化估计加速度，分别拟合正向和反向：

```text
a_ball = A × cnt + B
cnt_zero = -B / A
```

取两个方向所得零点的中值用于检查几何模型基准。当前基础鲁棒性调参阶段明确令
`zero_trim Ki=0`，不让人工拨动、截停或工具遮挡写入长期偏置；待基础控制稳定后，才考虑
在中心小误差、低速且无扰动的监督窗口内启用带泄漏的小范围偏置学习。

### 2.2 非线性控制律

控制器采用非线性串级结构。先把球速折算成制动距离，形成相平面停止坐标：

```text
s = error + velocity × |velocity| / (2 × 200 mm/s²)
v_ref = -80 mm/s × tanh(s / 45 mm)
e_v = velocity - v_ref
u_req = -3.0° × tanh(e_v / 55 mm/s) + u_acc + zero_trim
```

第一项的 `v|v|/(2a_b)` 带方向：球若快速靠近中心且剩余距离不足，`s` 会在位置过零之前
先翻号，目标速度随即反向，速度内环提前给制动角。距离较近时目标速度和角度都小，距离
较远时平滑趋近上限，且 `tanh` 在远端的导数逐渐减小，不产生分段跳变。基础控制角限制为
`±3.0°`；物理边界仍为 `-6.7°~+4.7°`，只作为连杆/编码器最终保护，不用于日常打满。

角度变化率按位置误差调度：

```text
rate_normal = 10 + (32 - 10) / (1 + (|error| / 30 mm)^2)  [deg/s]
rate_brake = 48 deg/s, when velocity × u_cmd < 0 and |velocity| > 5 mm/s
```

普通纠偏中心附近约 `32°/s`、远端渐近 `10°/s`，维持“远端目标更大但变化更慢”；外界
拨动后若命令方向正在消除现有速度，则临时提高到 `48°/s`，优先卸掉动能。

当 `|error|>=5 mm`、树莓派报告 `MOVING=0`、连续位置变化不超过 `0.5 mm`，同时控制器仍
请求至少 `0.5°`，持续 `0.4 s` 后判为工具截停或黏滞卡住。此时把控制倾角限制到
`±0.7°`，避免释放瞬间携带大倾角；位置重新变化或 `MOVING=1` 后立即解除。该机制不是
safe return，不命令步进电机去某个“水平 count”，失链时依旧保持当前角度。

速度差分得到的加速度先限幅到 `±1500 mm/s²`，再以 `0.15 s` 时间常数低通。当前
`Ka=0`，只通过 Debug_Ex 回传而不参与输出：滚球是以位置和速度为完整状态的二阶对象，
加速度由水管角和扰动决定，直接反馈一个带噪、带延迟的差分量很容易放大抖动。只有实机日志
证明估计足够平滑且有可重复的未建模扰动后，才小步启用 `u_acc=-Ka×a_filtered`。

## 3. 启动条件

H3 按“树莓派回传足够可靠”的策略接管：

- 球在中心 ±120 mm 内，覆盖水管主要有效区域；
- 收到过一帧 CRC 与协议版本正确的 `VALID=1` 数据；
- 总测量龄不超过 200 ms；只需一拍即可接管。

`QUALITY`、`V_VALID`、60 ms 降级标志和之后偶发的单帧 `INVALID` 仍会显示和统计，
但不再让 H3 退出闭环。单帧无效时继续使用最近一次有效位置，直到 200 ms 总超时。

控制器内部稳定判据为 `|x|<=2 mm`、`|v|<=5 mm/s` 连续 1 s。基础控制命令为 `±3°`，
动态角速度为普通 `10~32°/s`、制动 `48°/s`；零偏积分当前关闭。最终目标仍会被
`-6.7°~+4.7°` 的连杆物理边界和步进电机编码器软限位夹住。

## 4. 失效行为

- 单个 `VALID=0`、速度标志或质量不足：继续使用最近一次有效位置闭环；
- 进入 H3 时保持当前水管角等待首帧视觉，不先去机械水平标定位置；
- 总测量龄超过 200 ms：立即停止脉冲并保持失链瞬间的水管角，等待视觉恢复；
- 退出 H3 时同样就地保持，不自动回水平位；
- 步进限位守护进入 `FAULT`：任务进入系统故障页，驱动层已经停机失能。

这里刻意不使用几何模型的水平 count 做 safe return：水平标定存在偏差时，盲目
回零可能形成持续斜坡并把钢珠送到水管一端。通信恢复后，控制器从实际保持角重新初始化，
再由树莓派位置反馈接管。编码器机械软限位仍然全程有效。

## 5. 首次上板顺序

1. 抬起/取下球，验证进入 H3 后水管就地保持，不能先自动回某个水平 count。
2. 用 UART 测试发送器分别发送 `x=+10 mm` 和 `x=-10 mm`：前者必须令目标 cnt 下降，后者上升。
3. 接真实视觉，手推球确认 `X/V` 符号、帧率、测量龄和 `QUALITY`。
4. 将球放在中心附近，扶住两端挡片后短时闭环；先核对方向，再逐步放手。
5. 用 `Debug_Ex/UART1`（115200 8N1）记录 `[BALL]` 遥测，再调整机械标定值和控制增益：

   ```powershell
   python tools/visualizers/ball_balance_viz.py --port COM7 --csv ball.csv --log ball_raw.txt
   ```

   H3 以 20 Hz 输出树莓派原始位置 `xr`、控制位置 `x`、原始速度 `v`、停止坐标 `stop`、
   目标速度 `vref`、速度误差 `ev`、低通加速度、实际/命令水管角和速度环反馈，并用
   `brk/stuck/px` 标识制动、截停和匀速位置补偿。它也回传动态角速度、零偏、限幅状态和
   树莓派链路统计；进入任务时的 `[BALLCFG]` 行给出本次固件实际使用的全部关键参数。若 `drop` 持续
   增长，说明 Debug_Ex 输出缓冲来不及发送，此时采样不完整，应先排查串口连接或降低输出频率。

## 6. OLED 实时页面

H3 页面以约 `10 Hz` 更新 `x/v`、编码器当前/目标计数、命令角/零偏和测量龄/质量。
此前页面在 `ACTIVE` 状态只在状态或 `settled` 翻转时渲染，导致闭环数据实际持续变化，
OLED 却长时间停在接管瞬间的旧值。这是应用层刷新门控造成的确定性冻结，并非树莓派停止
回传或 OLED DMA 失效。

旧门控建立在“整帧 OLED 刷新会阻塞约 26 ms”的历史假设上；当前驱动已经采用双缓冲 DMA，
约 23 ms 的 I2C1 整帧传输在后台完成。H3 现在对所有状态按 100 ms 周期请求刷新，并在
`Ui_IsFlushBusy()` 为 true 时直接跳过该控制拍，不调用会等待上一帧完成的 `OLED_Flush()`。
状态变化若恰逢 DMA 忙，不会丢失：渲染快照仍保持旧值，后续 20 ms 控制拍会继续重试。

当前仍有一项架构债务：RUN 模式下 `App_UiTick()` 不渲染，任务只能在自己的 20 ms 控制
回调中调用 UI。忙时跳过已避免已知长等待，但长期更合理的做法是给任务增加独立
`on_ui_tick`/状态快照，让控制计算与 OLED 文本格式化彻底分离。完整高速诊断仍以 20 Hz
Debug_Ex `[BALL]` 为准，OLED 只承担现场概览。

## 7. 2026-07-31 串口实测发现

此前记录中，球位置长时间稳定在约 `7.7~8 mm`、树莓派 `MOVING=0`，但旧 H3 遥测速度仍约
`-6.8 mm/s`。串口帧率、CRC、丢帧和 Debug_Ex 丢字节均正常，因此问题不在树莓派数据质量，
而在 MCU 的 `RpiUart_Predict()`：它无条件叠加
`a=(5/7)g sin(theta)`，忽略静摩擦，在约 `-1.3°` 水管角和约 `43 ms` 测量龄下凭空生成了
速度。正式扰动日志还显示旧 `zero_trim` 会在人工拨动期间被改写，并在截停后保留约
`-1°` 偏置。

H3 现改用 `RpiUart_Observe()`：静止时原样使用树莓派 x/v；仅在 `MOVING=1` 时用原始速度
对位置做匀速时延补偿，绝不按水管角生成加速度或速度。旧 `RpiUart_Predict()` 暂时保留给
其他诊断页面，避免扩大本次修改范围。实测原始记录和分析报告位于工作区
`captures/h3/h3_20260731_010540_*`；事件键存在最多约 30 s 的人工标记滞后，判断扰动/截停
时刻应以位置、MOVING 和 INVALID 变化为主，不把事件键时间当作精确真值。
