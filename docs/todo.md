## 速度闭环：2026-07-29 上板实测结论

> 数据来自 Device Check「Duty Sweep」+「Speed PID」三段遥测（抬轮空载）。修复前 14153 拍、
> 修复后 16043 拍，两轮采集流程与判据一致。原「未验证推测」清单已按实测逐条结论化。

**修复已上板复测通过**（前后对比表见 `docs/changelog.md`）：停止时间 64.8 s 窗内未达成 →
**+0.14 s**；积分峰值 10.7 → 0.087（限值 0.667，未触限）；占空比饱和 5.83% → **0**；
稳态占空比 σ 6.9% → **0.26~0.55%**；稳态跟踪误差已降到编码器量化步长的 10% 以下。
下方「已实测确认并修复」各条均指修复前的实测现象。

**已实测确认并修复**（改动见 `docs/changelog.md`，控制律见 `docs/interfaces/middleware_chassis.md`）：

- **积分过度累积 / 停不下来**：`ki=17` 与 `integral_limit=96` 相差 16 倍（应按 `output_limit/ki`
  派生）。把目标顶到不可达值 11.9 s 后积分冲到 10.7（饱和参考线 5.88 的 1.8 倍），清零目标后
  **55 s 才退绕完、64.8 s 观测窗内轮子始终未停稳**。更关键的是这不只是限幅配错：目标为 0 时
  该环**没有收敛机制**——积分退绕速率正比于误差，车爬得越慢退得越慢，且起转死区内小占空比
  不产生运动、没有反馈。积分峰值仅 2.16 的那一段同样爬了整整 12.4 s。
  → 已改为「前馈 + PI」并对零目标特判（复位 PID + 主动刹车）。
- **起转死区 10%**：0~8% 占空比时两轮实测速度严格为 0。
- **占空比→速度高度线性**：左 `duty%=81.85v+1.03`、右 `duty%=77.25v+1.70`，10%~80% 区间
  拟合残差 < 2.4%；两轮增益差约 6%，前馈须分轮标定。→ 已作为前馈常数写入 `chassis.h`。
- **可达上限约 1.21 m/s**（100% 占空比），目标超过 1.45 m/s 即持续饱和。原 `SPD_MAX=3.0`
  是上限的 2.5 倍。→ 已改为 1.0。
- **反馈量化**：实测轮速严格落在 0.0295 m/s 的整数倍上；`kp=200` 时静止状态占空比
  **σ=6.9%、摆幅 −17%~+25%**。→ 已降 `kp` 到 60 并加 6 Hz 一阶低通。

**已排除**：

- **左右轮符号一致性**：正/负占空比下两轮速度符号均正确，当前接线不存在正反馈风险。
  （运行时守卫仍无，见下）
- **PID 实现本身**：用 `duty[i] = clamp(kp*e[i-1] + ki*integral[i-1], ±100)` 逐样本核对
  15010 个点，中位偏差 0.066%，固件行为与 `core/pid` 位置式公式完全一致。

**确认存在但影响很小，暂不处理**：

- **控制拍抖动**：长拍（27~32 ms）**每 208~210 ms 出现一次**，与 `CHK_UI_PERIOD_MS=200` 精确
  对应，源头是 OLED 阻塞刷屏（实测只占 7~11 ms，不是此前估的 26 ms）。恰好 10.0% 的拍受影响，
  而 PID 固定按 `dt=0.02` 积分 → **等效积分增益仅偏低约 3%**。修复后复测该分布完全未变
  （20 ms 占 90.0%、28~32 ms 占 10.0%、最大 32 ms），本次未处理。可顺手把渲染移出控制拍。

**仍未处理**：

1. **编码器脉冲「读-清」竞态**：GPIO A 相中断优先级 `0` 可抢占采样定时器优先级 `3`
   （已在生成代码中核实），`HallEncoder_UpdateSample` 的 `raw = pending_count; pending_count = 0;`
   非原子。本次遥测测不出来（概率低、主要影响里程慢漂）。根治：GPIO ISR 只维护**只增累计
   计数**，采样时取快照算增量（32 位读在 M0+ 原子）。
2. **提高编码器分辨率**：A 相双边沿（2×）或 AB 四倍频（4×），把量化噪声降到 3% 以内。
   比低通更优（无相位滞后），见 `control-plan.md` §2.4 第 3 条。
3. **速度环发散守卫**：连续 N 拍输出饱和且误差不收敛时抬 FAULT，防接线/符号改动后飞车。
4. **过零反转冲击**：PID 输出过零时 TB6612 硬切方向，近停转「读 B 相定向」最不可靠。
   加前馈后过零点附近的输出已连续，风险下降，但仍无斜率限制。
5. **前馈需落地后重标（优先级最高）**：现有四个常数是**抬轮空载**标定，落地负载更大、
   同占空比对应更低速度。不重标则前馈系统性欠出力、全靠 PI 补，等于退回小增益纯 PI，
   上面那组验证数据不成立。流程：落地重跑 Duty Sweep → 重新拟合 `CHASSIS_FF_*` 四常数。

## 延后的性能优化

### OLED 刷新 DMA 化 (Step 2, 已延后)

现状: `bsp/oled` 已完成帧缓冲重构 (commit `31baeec`, Step 1)——绘制只写 1KB RAM,
`OLED_Flush()` 用水平寻址**一次事务**发整帧 `[0x40][1024]`, 已消除旧版分包低效。
但该 Flush 目前仍是**阻塞**传输 (I2C1@400kHz, 整帧 ~26ms), 会占用控制环。

背景评估: MSPM0G3507 主频仅 **32MHz**(max 80MHz, 有余量), DMA **完全未用**(通道全空),
SRAM 32KB(仅用 ~8.5KB)。OLED 传输是 I2C 带宽瓶颈, 非 CPU 瓶颈; DMA 不缩短传输时间,
但能把那 ~26ms 从"CPU 忙等"变成"CPU 空闲"。

Step 2 待办 (让 Flush 全异步、CPU 近零):
1. **SysConfig**: 新增 DMA 模块 + 1 个通道, 配 I2C1(OLED) 的 TX DMA 触发事件; 给
   I2C1 加 STOP 中断(intController); 用 SysConfig CLI 重生成
   `ti_msp_dl_config` (仅确认新增 DMA/中断配置, 勿污染其它)。
2. **oled.c**: OLED_Flush 改为——设窗口(阻塞小命令) → 配 DMA(src=oled_fb, dst=I2C1 TX
   FIFO, 1025 字节, 8bit) → 启动 I2C 传输 → 立即返回; 加 busy 标志防重入(DMA 未完时新
   Flush 等待或跳过, 渲染周期 400ms 远大于 ~26ms 传输, 实际不重叠)。
3. **新增 `I2C1_IRQHandler`** (BSP 自持, 见 architecture.md 中断策略): STOP 中断清 busy。

可选进一步: I2C1 升 Fast Mode Plus (1MHz) 把整帧传输 ~26ms 降到 ~10ms (需 SSD1306
与走线支持); 属独立小改, 与 DMA 正交。

建议时机: 集成阶段(与 JY61P 的 I2C 统筹)一并做, 或控制环对 OLED 阻塞敏感时再做。
